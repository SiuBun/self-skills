# Android API 契约迁移

## 目标与边界

将现有 Android 客户端已接入的 API 与新文档逐项对应，按文档更新请求路径、请求参数和响应/请求实体映射。以用户指定的接口起点和范围为准，不把任务扩展成补齐文档中所有尚未实现的 API。

本 skill 负责协议迁移，不负责重新设计 Repository、会话、网络客户端或 UI 架构。优先保留现有调用链、业务参数值和协议之外的行为。

## 核心规则

1. 同时查看旧文档、新文档和当前代码。旧文档用于确认现有实现对应的接口语义，新文档用于确认目标契约；不要仅按混淆 Key 的字面含义推断映射。
2. 先按语义和接口用途匹配页面，再确认 URL、HTTP 方法、参数位置、参数名、类型及响应示例。相似名称不代表同一接口；例如批量打招呼与支持取消打招呼的单用户操作可能是不同端点。
3. 只更新用户要求范围内、代码当前已接入且能由文档确认的接口。文档中的可选新 API 不自动视为需要新增。
4. 对已有字段只更新序列化名，不顺手改变字段类型、默认值、业务参数值或业务行为，除非新契约明确要求且任务范围包含该变更。
5. 新增且被当前客户端需要的字段，使用文档确认的类型和序列化名，并补充有意义的字段说明。文档未提及的现有字段按用户要求注释掉，不要直接删除；同时检查其他接口是否共用该实体，避免破坏仍需要它的调用方。
6. 不因文档描述的请求形式自行改变 Retrofit 编码方式（如 `@Query`、`@Field`、`@Body`）或 HTTP 方法，除非用户要求同步该部分且文档和现有调用方式足以确认改动。存在冲突时保留现状并列出，必要时询问。
7. 文档不明确、示例与字段表矛盾、或无法确定请求用途时，不猜测。跳过该项，并在交付说明中列出页面/接口及具体不确定处。
8. 区分 API 接口和打开网页的 URL。网页 URL 也可能对应 API 文档中的协议/内容接口；找到明确的新文档后应检查其路径和参数名，但保留原 host 和业务参数值，除非文档或用户要求更改。协议页允许值不包含现有值时，不擅自改值，明确标注待确认。
9. 不清理或暂存无关工作区改动。提交时只选择本次任务文件。

## 文档读取

ShowDoc 常使用 SPA Hash URL，直接抓网页可能只得到应用外壳。若文档公开可读，可通过其页面数据接口读取目录和正文：

```text
POST /mydoc/api/item/info
Content-Type: application/x-www-form-urlencoded
item_id=<项目 ID>

POST /mydoc/api/page/info
Content-Type: application/x-www-form-urlencoded
page_id=<页面 ID>
```

从目录递归查找相关页面，并以页面 ID 读取正文。不要将项目 ID、页面 ID 混淆。若接口不可访问、要求登录或权限不足，停止尝试绕过访问控制；记录阻塞并请求用户提供可访问文档。

## 执行步骤

### 1. 确定范围并盘点实现

- 从用户指定的接口、章节或 `HTTPUrl` 中某个锚点确定起止范围；保留范围内既有顺序和名称。
- 检查 URL 常量、直接拼接的完整 URL、API 接口、请求 DTO、响应实体、Repository 中构造的 QueryMap/Body，以及相关调用点。
- 区分接口 URL 与打开协议、隐私、删除说明等页面的 URL helper；不要因其不在常量列表里就漏掉。
- 记录当前 HTTP 方法、参数传递位置和业务调用传入的值，作为改动前基线。
- 检查被多个接口复用的 DTO。某一接口缺少字段不代表其他接口也没有该字段。

### 2. 建立新旧文档映射

对每个已接入接口确认：

| 项目 | 核对内容 |
| --- | --- |
| 身份 | 文档标题、用途、用户指定范围与代码接口是否一致 |
| 地址 | 新请求 URL 的 path；完整网页 URL 还核对 host 和 query |
| 请求 | HTTP method、Query/Body/Form 位置、参数名、类型、必选性、示例值 |
| 响应 | 成功示例、字段表、嵌套对象和返回实体 |
| 冲突 | 旧文档与新文档差异、示例与字段表不一致、参数含义不明确 |

字段映射必须来自文档明确的对应关系或同一接口的字段说明，不根据相似拼写、其他接口的同名字段或代码旧注释推测。

### 3. 更新所有协议表面

- 更新 URL 常量或完整 URL helper；避免只改 Retrofit 注解而遗漏仍在使用的旧路径。
- 更新 API 注解中的请求参数名。若 Repository 使用 `QueryMap` 或手工 JSON/Form Map，同步其 Key。
- 在请求和响应实体中更新 `@SerializedName`。文档明确新增且客户端需要的字段才新增；对未文档化字段按要求保留为注释。
- 更新 KDoc 中的服务端字段名，确保与新 `@SerializedName` 一致；避免注释继续引用旧 key。
- 对字段共用实体进行调用方核对。若一个调用方的文档不包含某字段，不要在共享 DTO 上盲目注释掉而破坏其他已确认接口。
- 如用户要求保持已有参数值，保留调用方值，只改协议 Key。不要擅自将 `terms`、`privacy`、`Delete` 等业务值互换。
- 对新文档中存在但代码没有对应实现的接口，不自动新建；仅在范围要求新增时实现。

### 4. 歧义处理和报告

当文档页面找不到、多个候选接口用途不同、示例和参数表冲突、成功响应字段不一致或现有参数值不在新文档允许值中时：

- 只实施已确认的部分；
- 不通过猜测补 URL、参数、DTO 字段或默认值；
- 将未改项按接口名称、文档页和原因逐项列出；
- 只有继续实现必须由用户作出选择时才询问；若用户要求跳过，则直接跳过并报告。

### 5. 审查与验证

- 检查范围内旧 URL、旧 `@Query`/`@Field` key、旧 `@SerializedName` 和过期 KDoc；逐个确认残留是否属于范围外接口或其他版本，不做无差别替换。
- 查看完整 diff，确认请求参数值和调用行为未被意外改变，且未新增用户未要求的接口。
- 运行 `git diff --check`。
- Android 项目按实际 product flavor 选择 Kotlin 编译任务；如果 `:app:compileDebugKotlin` 因多个 variant 有歧义，使用明确任务名，例如 `:app:compileGoogleDebugKotlin` 和 `:app:compileLocalDebugKotlin`。
- 编译失败时修复由本次协议改动造成的问题；区分并报告原有警告或无关故障。
- 最终简要说明：已更新范围、明确跳过项及原因、验证命令和结果。不要声称未核实的完整性。
