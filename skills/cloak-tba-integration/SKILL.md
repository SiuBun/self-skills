# Cloak 和 TBA 接入

目标是先弄清当前项目实际上接入了 Cloak 和 TBA 的哪些内容，再从旧文档中确认这些代码的协议语义，最后只到新文档的对应章节查找新包映射。

本技能不是完整 TBA 接入指南，也不负责通用 Android 架构、会话生命周期、网络层设计或埋点业务规划。它只处理“现有项目协议实现 -> 旧文档标准字段 -> 新文档包级协议”的识别和迁移，并使用独立 skill 目录，不依赖其他 skill 的文件。

范围公式：

```text
本次迁移范围 = 当前项目活动代码实际发送的内容 ∩ 旧文档能确认的接入内容
目标协议 = 对上述每个标准字段，在新文档中查到的新 Key、分组、枚举和系统事件
```

不能直接拿新文档的全部字段与项目做差集，否则会把“包协议迁移”错误扩大成“补齐完整接入”。

## 核心原则

1. 同时读取旧包文档、新包文档和现有代码，不能只按新文档重新实现一套。
2. 先确定现有代码对应旧文档中的标准字段，再通过标准字段找到新文档中的新 Key。
3. 只迁移代码已经使用的字段和系统事件；新文档新增但项目从未使用的可选字段默认不补。
4. 新文档删除且没有等价字段的旧字段应从对应 payload 中移除。
5. 保留业务自定义事件名和属性名。只修改协议要求的事件字段、属性后缀、外层结构和系统事件值。
6. 不因文档中的接入建议顺带修改队列、持久化、重试次数、批量大小、冷启动时机或页面触发逻辑。
7. 不根据混淆 Key 的英文单词含义猜测字段；以文档中的“标准 Key”和代码注释为准。

## 第一阶段：盘点项目实际接入内容

先读代码，再决定需要看文档的哪些章节。不能先通读新文档后把所有内容往项目里套。

### 1. 找到协议入口

优先搜索：

```text
CloakParamNames
TbaFieldNames
TbaRepository
CloakRepository
RiskApi
TbaService
createCloakParams
enqueueInstall
enqueueSession
postInstall
postSession
tba_url
```

若项目命名不同，继续搜索：

- Cloak 请求域名、返回字符串和审核态判断；
- TBA URL、Retrofit 动态 URL 和事件批量数组；
- 自定义事件统一入口，如 `tba(...)`、`track(...)`、`enqueue(...)`；
- Install Referrer 回调；
- session 固定事件字符串；
- 属性后缀拼接代码；
- 每条日志生成 UUID 的位置。

### 2. 区分“定义过”和“实际使用”

以下内容不能直接算作当前接入范围：

- 字段映射类中声明但 payload 从未读取的属性；
- 整段注释掉的旧实现；
- 没有调用方的 `postInstall()`、`postSession()`；
- 历史 flavor 或废弃接口中的旧 URL；
- 新文档存在、但当前代码从未构建的广告事件或全局属性。

只有满足以下任一条件才纳入：

- 活动代码实际写入请求 Map/JSON；
- 活动代码实际调用固定系统事件；
- flavor 资源实际被当前构建读取；
- Cloak 响应值实际参与审核态或模式判断。

### 3. 形成当前接入清单

修改前先在分析中形成以下清单：

| 接入面 | 代码位置 | 当前发送结构 | 当前 Key/值 | 是否有活动调用 |
| --- | --- | --- | --- | --- |
| Cloak | 参数构建器/API | Query 或 JSON Body | 当前参数与 OS 枚举 | 是/否 |
| TBA 公共字段 | body 构建器 | 顶层分组 | 当前分组和字段 | 是/否 |
| 自定义事件 | 统一事件入口 | 事件 Key + 属性后缀 | 当前值 | 是/否 |
| install | Referrer 回调/Repository | 平铺或子对象 | 当前字段 | 是/否 |
| session | Activity/Application/Repository | 固定事件或空对象 | 当前值 | 是/否 |
| 用户属性 | 初始化或页面 | 普通事件或专用结构 | 当前事件值 | 是/否 |

这张表决定后续要读取的文档章节。项目没接入的部分不继续展开。

## 读取运营平台文档

文档 URL 通常是前端 Hash 路由：

```text
https://market.gte666.com/#/appmeta/doc/<docId>
https://market.gte666.com/?#/appmeta/doc/<docId>
```

直接抓取页面只能得到站点外壳。可从 URL 提取 `docId`，通过公开接口读取正文：

```text
GET https://market.gte666.com/meta/app-doc/get?docId=<docId>
```

响应中的 `doc` 字段是 Markdown。分别保存新旧正文后进行 diff。

根据项目接入清单定向读取：

| 项目中发现的内容 | 旧、新文档中要找的章节 |
| --- | --- |
| Cloak URL、参数、返回值 | “信息”中的 Cloak 地址、“Cloak 接入” |
| TBA URL | “信息”中的测试/正式地址 |
| TBA 公共字段和分组 | “格式 -> 通用字段” |
| 自定义事件和属性 | “埋点” |
| install | “install 事件”及样例 |
| session | “session 事件”及样例 |
| 用户属性 | “自定义用户属性-添加/删除” |
| 全局事件属性 | “自定义全局事件属性”，仅项目已使用时 |
| 广告事件 | “广告事件”，仅项目已使用时 |

重点核对：

- 测试、正式和 Cloak 地址；
- Cloak 命中与正常返回值；
- Cloak 参数 Key 和 OS 枚举；
- TBA 顶层分组；
- 自定义事件字段和参数后缀；
- install 外层结构、字段和枚举；
- session 结构和系统事件值；
- 用户属性添加、删除的系统事件值。

接口失效时再检查站点入口 JS 和文档页面 chunk，定位当前文档 API；不要把登录页 HTML 当作文档内容。

## 第二阶段：用旧文档解释现有代码

不要直接比较旧 Key 和新 Key。先建立语义中间层：

| 代码位置 | 标准字段 | 旧文档 Key/结构 | 新文档 Key/结构 | 动作 |
| --- | --- | --- | --- | --- |
| Cloak 参数 | bundle_id | 旧 Key | 新 Key | 替换 |
| TBA 公共字段 | log_id | 旧分组.旧 Key | 新分组.新 Key | 移动并替换 |
| install | lat | 旧枚举 | 新枚举 | 替换枚举 |
| session | session | 旧子对象或事件 | 新顶层字段或事件 | 调整结构 |

字段迁移判断顺序：

1. 读取代码注释或变量用途，确定标准字段。
2. 在旧文档中验证当前 Key、分组和枚举确实匹配。
3. 在新文档中按同一标准字段查找新 Key、分组和枚举。
4. 判断只是字符串替换，还是字段移动、嵌套方式变化。
5. 新文档无对应字段时删除该协议字段，不自行寻找名称相近的替代项。

旧文档的作用是“解码当前代码”，不是旧包参考资料的简单存档。例如代码发送 `tour`，必须先从旧文档确认它是 `bundle_id`，再去新文档查 `bundle_id`；不能因为新文档中某个 Key 看起来像包名就直接替换。

当代码注释与旧文档冲突时：

1. 以实际写入的旧 Key 在旧文档中的定义为主要证据；
2. 对照旧文档样例确认分组；
3. 检查调用方传入值是否符合该标准字段；
4. 仍无法确认时停止修改该字段并向用户说明，不猜测。

## 第三阶段：在新文档中重新编码

对当前接入清单中的每一项，使用标准字段在新文档中查找：

- 新混淆 Key；
- 新顶层分组；
- 新枚举值；
- 新系统事件 Key 和固定值；
- 是平铺字段还是独立 JSON 子对象；
- 测试、正式和 Cloak 地址；
- Cloak 响应值。

迁移完成后，代码发送的业务数据来源和调用时机应保持原样，变化只体现在新包协议要求的位置和值。

## Cloak 迁移

通常需要检查并同步：

- `bundle_id`、`os`、`app_version`、`distinct_id`、`client_ts`；
- `device_model`、`os_version`、`gaid`、`android_id`；
- 文档要求且现有代码已经发送的其他参数；
- Android 对应的新 OS 枚举；
- 命中黑名单和正常模式的返回字符串；
- Cloak 请求地址。

修改边界：

- 参数 Key 放在统一的字段映射类中，调用方继续按标准语义组装。
- 枚举值属于协议字符串，应随新文档更新。
- 不因为新文档推荐 POST 就自动把现有 GET 改成 POST；只有用户要求完整校正或现有请求无法表达新结构时才改传输方式。
- 不顺带改变 `distinct_id`、Android ID、GAID 的生成和持久化策略。

## TBA 公共字段迁移

不同包可能不仅 Key 不同，顶层分组也完全不同。字段必须移动到新文档指定的分组，不能只替换字符串。

推荐让字段模型表达文档中的当前分组，例如：

```kotlin
data class TbaFieldNames(
    val firstGroupKey: String,
    val secondGroupKey: String,
    val eventKey: String,
    val paramSuffix: String,
    val firstGroup: FirstGroup,
    val secondGroup: SecondGroup,
)
```

若旧模型的 `Common/App/Device/Support` 已与新文档结构不一致，应按新分组重命名，避免后续把字段放回错误位置。

迁移时保持原有取值逻辑：

- 原来如何取得 app version、设备 ID、机型、运营商和语言，迁移后继续使用原来源。
- 原来每条事件生成一次 `log_id`，迁移后只移动字段位置，不改变生成频率。
- 文档虽然对值格式有更严格建议，但用户仅要求协议迁移时，不顺带修改时间单位、ID 策略或缺省值。

## 自定义事件

自定义业务事件名通常由运营定义，不随包协议自动改名。例如项目已有的页面点击、通话、充值事件继续保留。

只修改协议层：

- 顶层事件字段 Key；
- 属性名统一追加的新后缀；
- 全局事件属性容器 Key（仅当项目已接入）；
- 用户属性添加、删除的系统事件值。

所有普通事件应继续通过统一构建入口追加后缀，不能要求各业务调用方自行拼接。

## Install 事件

先判断旧、新文档的 install 结构：

- 系统事件名作为顶层字段和值；
- install 字段平铺在顶层；
- 或使用事件名称作为独立 JSON 子对象的 Key。

如果新文档改为独立子对象，应先构建原有公共字段，再放入 install 对象：

```kotlin
val body = buildCommonBody(names)
body[names.install.eventKey] = installParams
```

不要为了复用普通事件构建器而额外写入新文档没有要求的普通事件字段。

逐项迁移现有 install 字段：

- build；
- user_agent；
- lat 及其枚举；
- first install、last update；
- referrer URL 和 install version；
- 四个 referrer 时间戳。

旧文档存在、但新文档没有对应项的 install 字段应移除。除非用户要求完整接入，否则不修改“只发一次”、Install Referrer 获取时机、队列策略或成功标记。

## Session 事件

session 常见变化包括：

- 旧协议使用独立空对象；
- 新协议使用顶层事件字段和固定值；
- 或固定事件名称发生变化。

只调整 payload 结构和系统事件值。现有代码是在冷启动、进入主界面还是每次 resume 发送，应保持不变。

## 用户属性

如果项目已经实现用户属性添加或删除：

- 更新新文档约定的系统事件名；
- 更新 `distinct_id` 对应的新 Key；
- 保持现有属性集合、调用位置和发送方式。

新文档对“只需公共字段中的 distinct_id”有额外要求时，若用户只要求从旧协议迁移到新协议，不主动重写专用 body；先保持原业务构建逻辑，只替换当前实现所对应的协议字段。

## 实施步骤

1. 检查工作树，不能覆盖用户已有修改。
2. 搜索活动代码，形成当前项目接入清单。
3. 读取旧文档，只定位清单中每个当前 Key 对应的标准字段。
4. 读取新文档，只查这些标准字段的新 Key、分组、枚举和系统事件。
5. 列出“代码位置 -> 旧 Key -> 标准字段 -> 新 Key/结构”的迁移表。
6. 先修改字段映射类，再修改 payload 分组和系统事件。
7. 更新活动 flavor 中确实发生变化的地址和 Cloak 返回值。
8. 搜索旧 Key、旧分组、旧枚举和旧系统事件，确认活动代码中没有遗漏。
9. 编译所有受影响的 Debug flavor；若只有一个变体，编译该变体。
10. 检查 diff，确认没有新增项目原本未接入的文档能力，也没有改动队列、定时器、缓存、重试和业务触发位置。

## 完成前检查

1. Cloak 参数是否全部来自项目原有字段，没有擅自新增可选参数。
2. Cloak OS 枚举、返回值和地址是否属于新包。
3. TBA 每个已使用字段是否位于新文档指定分组。
4. 普通事件是否使用新的事件 Key 和属性后缀。
5. install 是否符合新文档的平铺或嵌套结构。
6. session 是否使用新的系统事件结构和值。
7. 用户属性系统事件和 distinct ID Key 是否已映射。
8. 新文档删除的旧字段是否已经从对应 payload 移除。
9. 自定义业务事件名和属性名是否保持不变。
10. 队列、flush、失败处理和发送时机是否未被无关修改。

## 维护此技能

- 不记录单个包的具体混淆 Key；这些值应始终以当次运营平台文档为准。
- 只沉淀跨包稳定的迁移方法、范围控制和验证规则。
- 若运营平台文档入口或 API 变化，更新“读取运营平台文档”章节。
- 若后续项目确认必须同步修改队列或生命周期策略，将其作为用户明确选择的完整接入模式，不改变本技能默认的最小协议迁移边界。
